## 0. 먼저 알아둘 것

### DB 연결에 필요한 재료 세 가지

| 재료 | 위치 | 역할 |
| :--- | :--- | :--- |
| JPA 의존성 `spring-boot-starter-data-jpa` | `build.gradle.kts` | DB를 **자바 객체로** 다루는 방법 |
| MariaDB 드라이버 `mariadb-java-client` | `build.gradle.kts` | MariaDB 제품과 **실제로 통신**하는 방법 |
| 접속 설정 `spring.datasource.*` | `application.properties` | **어디로** 붙을지 (주소·계정) |

하나라도 빠지면 막히는 지점이 다릅니다: 의존성이 없으면 **클래스를 못 찾아** 컴파일/기동 단계에서, 드라이버가 없으면 **접속 단계**에서, URL이 없으면 **어디로 갈지 몰라** 접속 단계에서 막힙니다.

### 접속 주소(JDBC URL) 네 조각

`jdbc:mariadb://localhost:3307/springboot`

| 조각 | 값 | 짝이 되는 재료 |
| :--- | :--- | :--- |
| ① 프로토콜 | `jdbc` | JDBC 방식으로 접속 |
| ② DB 제품 | `mariadb` | MariaDB 드라이버 |
| ③ 호스트 : 포트 | `localhost:3307` | **DB 서버**의 포트 (스프링 앱의 8080과 다름. 이 가이드는 컨테이너의 3306을 내 컴퓨터 3307로 연결) |
| ④ 데이터베이스 이름 | `springboot` | 서버 안의 DB (**내가 먼저 만들어야** 함) |

- 계정·비밀번호는 `application.properties`에 **평문**으로 들어갑니다. 그래서 학습용 설정이며, 값은 외우는 정답이 아니라 **내 환경 값으로 바꿀 대상**입니다.

### 자바 클래스 → 테이블 번역 (JPA)

| 자바 쪽 | 테이블 쪽 | 비고 |
| :--- | :--- | :--- |
| `@Entity` 클래스 | 테이블 | 없으면 JPA가 이 클래스를 **아예 보지 않음** |
| `@Table(name = "product")` | 테이블 이름 | 생략해도 클래스 이름 기반으로 정해짐 |
| `@Id` 필드 | 기본키(PK) | 없으면 "이걸 뭘로 구분하지?"에서 막힘 |
| `@GeneratedValue(IDENTITY)` | `auto_increment` | **DB가** 번호를 만들어 줌 |
| 필드 | column | **`@Column`이 없어도 column이 생김** |
| `@Column(nullable = false)` | `not null` | column을 "만드는" 게 아니라 **규칙을 덧붙임** |

- 애너테이션은 두 집안에서 옵니다: `jakarta.persistence.*` = **JPA가 읽는 것**, `lombok.*` = **컴파일 때 코드를 만들어 주는 것** (`@Getter` `@Setter` `@NoArgsConstructor` `@AllArgsConstructor` `@EqualsAndHashCode` `@ToString`).
- Lombok이 만든 메서드는 소스에 안 보이고 빌드 결과에만 있습니다.
- Java `createdAt`처럼 가운데 대문자가 섞인 필드는 Spring Boot 기본 설정에서 **`created_at`** 으로 번역될 것으로 **예측**합니다 (Step 5에서 확인).

### 클래스가 네 개인 이유 — 모양이 다르면 클래스를 나눈다

| 클래스 | 역할 | 특징 |
| :--- | :--- | :--- |
| `Product` (엔티티) | DB에 저장되는 모양 | `number`, `createdAt`, `updatedAt` 포함 |
| `ProductDto` | 생성 요청으로 **받는** 모양 | `number` **없음** (아직 번호가 없으니까) |
| `ProductResponseDto` | 응답으로 **내보내는** 모양 | 시각 필드 **없음** |
| `ChangeProductNameDto` | 이름 변경 요청 | `number` + `name` 두 개만 |

- `price`·`stock`: 엔티티는 `Integer`(null 표현 가능), DTO는 `int`(null 불가). 엔티티에서 `nullable = false`로 null을 **막으려면** 먼저 null을 **표현할 수 있는 타입**이어야 합니다.

### `number`(ID)는 누가, 언제 만드나

```text
new Product()           → number 는 null
setName / setPrice ...   → number 는 건드리지 않음
productRepository.save() → DB가 INSERT 하며 auto_increment 로 번호 부여 → 돌아온 객체에 number 가 채워짐
```

- `number`를 만드는 주체는 **DB** (근거: `@GeneratedValue(strategy = GenerationType.IDENTITY)`).
- 반면 `createdAt`/`updatedAt`은 **자바 코드**(`LocalDateTime.now()`)가 채웁니다.

### 계층: 요청 한 번이 지나가는 길

```text
Controller → Service → DAO → Repository → (Hibernate) → MariaDB
 요청/응답     DTO↔엔티티    "무엇을 하려는가"   "어떻게 저장하는가"
 상태코드      변환·시각 채우기  insert/select...   save/findById/delete...
```

- `ProductRepository`는 **본문이 비어 있어도** `JpaRepository<Product, Long>`을 상속해서 `save`·`findById`·`delete` 등을 씁니다. 타입 인자 `Product`=엔티티, `Long`=`@Id` 필드 타입.
- DAO의 이름(`insertProduct`)과 Repository의 이름(`save`)이 다른 이유: DAO는 **무엇을 하려는가**, Repository는 **어떻게 저장하는가**.
- DAO의 `updateProductName`/`deleteProduct`는 **조회를 먼저 하고** 없으면 예외를 던지기 때문에 호출이 두 번(`findById` → `save`/`delete`) 들어가고 `throws Exception`이 붙습니다. `insert`/`select`는 대상이 없어도 되는 일이라 안 붙습니다.
- 조회가 두 가지: `getById/getReferenceById`(프록시 반환) vs `findById`(`Optional` — "값이 없을 수도 있다"를 타입으로 드러냄).

### `ddl-auto` — 가장 중요한 설정

| 값 | 기동 시 하는 일 | 어울리는 상황 |
| :--- | :--- | :--- |
| `create` | 기존 테이블을 **지우고 새로 만듦** → **데이터 전부 사라짐** | 학습 환경 |
| `update` | 없는 것만 추가, 기존 데이터 유지 | 개발 중 데이터를 남기고 싶을 때 |
| `validate` | 엔티티와 테이블이 맞는지 **검사만** | 운영 |
| `none` | 아무것도 안 함 | 운영 |

> ⚠️ `create`이면 **재시작할 때마다 데이터가 사라집니다.** 고장이 아니라 설정대로 동작한 것입니다. 이걸 모르면 "저장이 안 된다"고 오진합니다.
> `create`는 **테이블**을 만들지, **데이터베이스**를 만들지 않습니다. DB(`springboot`)는 내가 미리 만들어야 합니다.

### 접속이 안 될 때 — 5단계 진단 순서

| 순서 | 확인할 것 | 저장소 안에 근거가 있나 | 대표 증상 |
| :-: | :--- | :-: | :--- |
| 1 | 드라이버가 있나 | 있음 (`build.gradle.kts`) | 드라이버 클래스를 못 찾음 |
| 2 | URL·DB 이름이 맞나 | 있음 (`application.properties`) | `Unknown database ...` |
| 3 | 계정·비밀번호가 맞나 | 있음 (`application.properties`) | `Access denied for user ...` |
| 4 | MariaDB 컨테이너가 떠 있나 | **없음** (내 컴퓨터 상태, `docker compose ps` 또는 DBeaver 접속으로 확인) | `Communications link failure` / `Connection refused` |
| 5 | 테이블이 만들어졌나 | **없음** (내 DB 상태) | 콘솔의 `create table` 로그 / DBeaver에서 확인 |

- 4·5단계는 파일에 적힌 정보가 아니라 **실행 중인 상태**라서 저장소를 뒤져도 알 수 없습니다.

## Step 1: 준비

### 1-1. Docker 준비 (MariaDB를 따로 설치하지 않습니다)

MariaDB를 내 컴퓨터에 직접 설치하는 대신, **Docker 컨테이너**로 띄웁니다. 설치·삭제가 깔끔하고, 명령 한 줄(`docker compose up`)로 켜고 끌 수 있습니다.

1. **Docker Desktop**이 설치되어 있어야 합니다. (없으면 <https://www.docker.com/products/docker-desktop/> 에서 받아 설치 — 이것만 한 번 설치하면 됩니다. 설치 후 재부팅을 요구할 수 있습니다.)
2. Docker Desktop을 **실행**합니다. 창 왼쪽 아래에 초록색 `Engine running`이 보이면 준비 완료입니다.
3. 터미널(PowerShell 또는 Git Bash)에서 확인합니다.

```bash
docker --version          # 버전이 나오면 설치됨
docker compose version    # 버전이 나오면 compose 사용 가능
```

> ⚠️ **포트 주의:** 내 컴퓨터에 MySQL/MariaDB가 이미 설치되어 3306을 쓰고 있다면(DBeaver에 기존 연결이 있다면 그렇습니다), 같은 3306을 쓰면 충돌합니다. 이 가이드는 처음부터 **호스트 포트 3307**을 씁니다. 기존 MySQL 연결(3306)과 새 MariaDB 연결(3307)은 서로 다른 연결이니 헷갈리지 마세요. 3306이 비어 있어도 3307 그대로 따라 하면 됩니다.

> Docker Desktop이 꺼져 있으면 아래 모든 `docker` 명령이 실패합니다. 실습할 때마다 **먼저 Docker Desktop을 켜세요.**

### 1-2. `docker-compose.yml` 만들기

프로젝트 **맨 위 폴더**(`build.gradle.kts`가 있는 곳)에 `docker-compose.yml` 파일을 새로 만듭니다.

```yaml
services:
  mariadb:
    image: mariadb:11
    container_name: practice-mariadb
    ports:
      - "3307:3306"
    environment:
      MARIADB_ROOT_PASSWORD: root1234
      MARIADB_DATABASE: springboot
      MARIADB_USER: practice
      MARIADB_PASSWORD: practice1234
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
    volumes:
      - mariadb-data:/var/lib/mysql

volumes:
  mariadb-data:
```

| 줄 | 의미 |
| :--- | :--- |
| `image: mariadb:11` | 사용할 MariaDB 이미지 (처음 실행할 때 자동으로 내려받음 — 별도 다운로드 불필요) |
| `ports: "3307:3306"` | 내 컴퓨터 **3307** ↔ 컨테이너 3306. 내 컴퓨터에 이미 MySQL 등이 3306을 쓰고 있어도 충돌하지 않음. JDBC URL·DBeaver의 포트는 **3307** |
| `MARIADB_DATABASE: springboot` | 시작할 때 `springboot` **데이터베이스를 자동 생성** |
| `MARIADB_USER` / `MARIADB_PASSWORD` | 위 DB를 쓸 수 있는 계정 자동 생성 → `application.properties`의 `username`/`password` |
| `MARIADB_ROOT_PASSWORD` | 관리자(root) 비밀번호 (DBeaver 접속용) |
| `command: --character-set-server=utf8mb4` | 한글(`펜`)이 깨지지 않게 |
| `volumes: mariadb-data` | 컨테이너를 지워도 데이터가 남는 저장 공간 |

> 여기 적힌 `root1234`, `practice1234`는 **내 컴퓨터에서만 쓰는 실습용 값**입니다. 원하는 값으로 바꿔도 되지만, 바꾼 값은 1-6의 `application.properties`와 **반드시 같아야** 합니다.
> 이 파일에 비밀번호가 들어 있으므로, 진짜 쓰는 비밀번호는 넣지 말고 GitHub에 올릴 때도 주의하세요.

### 1-3. 실행하기 — `docker compose up`

`docker-compose.yml`이 있는 폴더에서 터미널을 열고:

```bash
docker compose up -d
```

- `-d`는 백그라운드 실행입니다 (터미널을 계속 쓸 수 있음).
- **처음 실행**은 MariaDB 이미지를 내려받느라 시간이 걸립니다. 이후에는 빠릅니다.

실행 확인 (5단계 진단표 4단계):

```bash
docker compose ps                          # practice-mariadb 의 STATUS 가 Up(running) 인가
docker compose logs mariadb --tail 5       # "ready for connections" 가 보이면 접속 가능
```

> 로그에 `ready for connections`가 **두 번** 나올 수 있습니다 (초기 설정 후 재시작). 마지막 줄이 `ready for connections`이면 됩니다. 이 메시지가 나오기 전에 앱을 실행하면 접속이 거절됩니다.

자주 쓰는 명령:

| 하고 싶은 일 | 명령 |
| :--- | :--- |
| 켜기 | `docker compose up -d` |
| 끄기 (데이터 유지) | `docker compose stop` |
| 끄고 컨테이너 삭제 (데이터 유지) | `docker compose down` |
| **데이터까지 완전 삭제** | `docker compose down -v` |
| 상태 보기 | `docker compose ps` |
| 로그 보기 | `docker compose logs mariadb` |

### 1-4. DBeaver로 접속하기

DBeaver는 DB를 눈으로 보고 SQL을 실행하는 도구입니다. 서버는 Docker 속 MariaDB, DBeaver는 그 서버에 접속하는 **클라이언트**입니다.

1. 컨테이너가 떠 있는지 확인합니다 (`docker compose ps`).
2. DBeaver 실행 → 왼쪽 위 **플러그 아이콘(새 데이터베이스 연결)** 클릭 (`Ctrl + Shift + N`).
3. 목록에서 **MariaDB** 선택 → Next.
4. **Main** 탭 입력 (앱이 쓸 계정으로 접속합니다):

| 항목 | 값 |
| :--- | :--- |
| Server Host | `localhost` |
| Port | `3307` |
| Database | `springboot` |
| Username | `practice` |
| Password | `practice1234` (compose 파일의 `MARIADB_PASSWORD`) |

5. 아래쪽 **Test Connection** 클릭.
   - "드라이버 파일을 다운로드할까요?" 창이 뜨면 **Download** (처음 한 번, 인터넷 필요).
   - `Connected`가 뜨면 성공 → **Finish**.
6. 왼쪽 목록의 연결을 펼치면 `springboot` 데이터베이스가 보입니다. 아직 테이블은 없습니다 (Step 5에서 앱이 만듭니다).

> `SELECT 1` 같은 SQL을 직접 실행해 보려면 연결을 선택하고 `Ctrl + ]`(SQL 편집기), 실행은 `Ctrl + Enter`입니다.
> 관리자 작업이 필요할 때만 Username `root` / Password `root1234`로 연결을 하나 더 만드세요.

### 1-5. 의존성

`build.gradle.kts`에 두 줄 추가 후 Gradle Reload

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-webmvc")
```

```java
package org.example.practice_spring.day05_jpa.data.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.time.LocalDateTime;
import lombok.AllArgsConstructor;
import lombok.EqualsAndHashCode;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import lombok.ToString;

/**
 * DB 의 product 테이블 한 행과 1:1 로 대응되는 클래스.
 * - jakarta.persistence.* : JPA 가 읽는 애너테이션 (테이블/column 번역 규칙)
 * - lombok.*              : 컴파일 때 getter/setter/생성자 등을 만들어 주는 애너테이션
 */
@Entity
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@EqualsAndHashCode
@ToString(exclude = "name")          // toString() 에서 name 만 뺀다
@Table(name = "product")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // 번호는 DB(auto_increment)가 만든다
    private Long number;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false)
    private Integer price;

    @Column(nullable = false)
    private Integer stock;

    // @Column 이 없어도 column 은 생긴다 (규칙을 덧붙이지 않았을 뿐)
    private LocalDateTime createdAt;

    private LocalDateTime updatedAt;
}
```

`data/dao/impl/ProductDAOImpl.java` — "어떻게 저장하는가"

```java
package org.example.practice_spring.day05_jpa.data.dao.impl;

import java.time.LocalDateTime;
import java.util.Optional;
import org.example.practice_spring.day05_jpa.data.dao.ProductDAO;
import org.example.practice_spring.day05_jpa.data.entity.Product;
import org.example.practice_spring.day05_jpa.data.repository.ProductRepository;
import org.springframework.stereotype.Component;

@Component
public class ProductDAOImpl implements ProductDAO {

    private final ProductRepository productRepository;

    // 생성자가 하나뿐이면 @Autowired 없이도 주입된다 (Day01)
    public ProductDAOImpl(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    // 저장: save 한 번
    @Override
    public Product insertProduct(Product product) {
        return productRepository.save(product);
    }

    // 조회: 프록시를 돌려주는 방식 (값이 없을 수도 있음을 타입으로 드러내지 않는다)
    @Override
    public Product selectProduct(Long number) {
        return productRepository.getReferenceById(number);
    }

    // 수정: 조회(findById) → 값 변경 → 저장(save), 호출이 두 번
    @Override
    public Product updateProductName(Long number, String name) throws Exception {
        Optional<Product> selectedProduct = productRepository.findById(number);

        Product updatedProduct;
        if (selectedProduct.isPresent()) {
            Product product = selectedProduct.get();

            product.setName(name);
            product.setUpdatedAt(LocalDateTime.now());

            updatedProduct = productRepository.save(product);
        } else {
            throw new Exception();
        }

        return updatedProduct;
    }

    // 삭제: 조회(findById) → 삭제(delete), 호출이 두 번
    @Override
    public void deleteProduct(Long number) throws Exception {
        Optional<Product> selectedProduct = productRepository.findById(number);

        if (selectedProduct.isPresent()) {
            productRepository.delete(selectedProduct.get());
        } else {
            throw new Exception();
        }
    }
}
```

> 강의는 `productRepository.getById(number)`를 썼습니다. 이 메서드는 오래전에 deprecated 되었고 Boot 4 쪽에서는 쓸 수 없을 수 있어, 같은 역할의 **`getReferenceById`** 로 바꿨습니다 (이 변경은 직접 컴파일해 확인하지 못했습니다 — 빨간 줄이 뜨면 IDE의 자동완성을 기준으로).
> `findById`는 `Optional`을 돌려줍니다. 그래서 `isPresent()`로 **확인한 뒤** `get()`으로 꺼냅니다.

**읽고 확인하기 (강의 4교시)**

| 질문 | 답 |
| :--- | :--- |
| `throws Exception`이 붙은 DAO 메서드 | `updateProductName`, `deleteProduct` — "대상이 없을 수도 있는" 일 |
| Repository 호출 횟수 (`grep -o "productRepository\." … \| wc -l`) | 6 (`save` 1 + `getReferenceById` 1 + `findById` 2 + `save` 1 + `delete` 1) |
| `@Override` 줄 수 (`grep -c`) | 4 — 메서드마다 하나지만 호출은 메서드 하나에 여러 번 나올 수 있어 다름 |
| 호출이 두 번인 메서드 | `updateProductName` (`findById` → `save`), `deleteProduct` (`findById` → `delete`) |

```java
package org.example.practice_spring.day05_jpa.service.impl;

import java.time.LocalDateTime;
import org.example.practice_spring.day05_jpa.data.dao.ProductDAO;
import org.example.practice_spring.day05_jpa.data.dto.ProductDto;
import org.example.practice_spring.day05_jpa.data.dto.ProductResponseDto;
import org.example.practice_spring.day05_jpa.data.entity.Product;
import org.example.practice_spring.day05_jpa.service.ProductService;
import org.springframework.stereotype.Service;

@Service
public class ProductServiceImpl implements ProductService {

    private final ProductDAO productDAO;

    public ProductServiceImpl(ProductDAO productDAO) {
        this.productDAO = productDAO;
    }

    @Override
    public ProductResponseDto getProduct(Long number) {
        Product product = productDAO.selectProduct(number);

        ProductResponseDto productResponseDto = new ProductResponseDto();
        productResponseDto.setNumber(product.getNumber());
        productResponseDto.setName(product.getName());
        productResponseDto.setPrice(product.getPrice());
        productResponseDto.setStock(product.getStock());

        return productResponseDto;
    }

    @Override
    public ProductResponseDto saveProduct(ProductDto productDto) {
        Product product = new Product();                       // 이 시점 number 는 null
        product.setName(productDto.getName());
        product.setPrice(productDto.getPrice());
        product.setStock(productDto.getStock());
        product.setCreatedAt(LocalDateTime.now());             // 시각은 자바 코드가 채운다
        product.setUpdatedAt(LocalDateTime.now());

        Product savedProduct = productDAO.insertProduct(product);   // 이 줄을 지나야 number 가 채워진다 (DB 가 만듦)

        ProductResponseDto productResponseDto = new ProductResponseDto();
        productResponseDto.setNumber(savedProduct.getNumber());
        productResponseDto.setName(savedProduct.getName());
        productResponseDto.setPrice(savedProduct.getPrice());
        productResponseDto.setStock(savedProduct.getStock());

        return productResponseDto;
    }

    @Override
    public ProductResponseDto changeProductName(Long number, String name) throws Exception {
        Product changedProduct = productDAO.updateProductName(number, name);

        ProductResponseDto productResponseDto = new ProductResponseDto();
        productResponseDto.setNumber(changedProduct.getNumber());
        productResponseDto.setName(changedProduct.getName());
        productResponseDto.setPrice(changedProduct.getPrice());
        productResponseDto.setStock(changedProduct.getStock());

        return productResponseDto;
    }

    @Override
    public void deleteProduct(Long number) throws Exception {
        productDAO.deleteProduct(number);
    }
}
```

`controller/ProductController.java`

```java
package org.example.practice_spring.day05_jpa.controller;

import org.example.practice_spring.day05_jpa.data.dto.ChangeProductNameDto;
import org.example.practice_spring.day05_jpa.data.dto.ProductDto;
import org.example.practice_spring.day05_jpa.data.dto.ProductResponseDto;
import org.example.practice_spring.day05_jpa.service.ProductService;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

/**
 * 요청 받기 / 상태코드 정하기만 한다.
 * DTO↔엔티티 변환과 시각 채우기는 Service, 저장은 DAO·Repository 가 한다.
 */
@RestController
@RequestMapping("/product")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    // GET /product?number=1   (애너테이션 없이 받은 Long -> query 로 들어온다)
    @GetMapping()
    public ResponseEntity<ProductResponseDto> getProduct(Long number) {
        ProductResponseDto productResponseDto = productService.getProduct(number);

        return ResponseEntity.status(HttpStatus.OK).body(productResponseDto);
    }

    // POST /product   body: {"name":"펜","price":1000,"stock":100}
    @PostMapping()
    public ResponseEntity<ProductResponseDto> createProduct(@RequestBody ProductDto productDto) {
        ProductResponseDto productResponseDto = productService.saveProduct(productDto);

        return ResponseEntity.status(HttpStatus.OK).body(productResponseDto);
    }

    // PUT /product    body: {"number":1,"name":"볼펜"}
    @PutMapping()
    public ResponseEntity<ProductResponseDto> changeProductName(
            @RequestBody ChangeProductNameDto changeProductNameDto) throws Exception {
        ProductResponseDto productResponseDto = productService.changeProductName(
                changeProductNameDto.getNumber(),
                changeProductNameDto.getName());

        return ResponseEntity.status(HttpStatus.OK).body(productResponseDto);
    }

    // DELETE /product?number=1
    @DeleteMapping()
    public ResponseEntity<String> deleteProduct(Long number) throws Exception {
        productService.deleteProduct(number);

        return ResponseEntity.status(HttpStatus.OK).body("정상적으로 삭제되었습니다.");
    }
```

**예측 → 확인** (콘솔)

콘솔에서 `create table`로 시작하는 문장을 찾으세요. 먼저 아래를 보지 말고 `Product.java`만 근거로 예측해 보고 대조합니다.

```sql
-- 예측입니다. 실제 문장은 하이버네이트(Hibernate 7)가 만듭니다. 타입·옵션 표기는 다를 수 있습니다.
create table product (
    number bigint not null auto_increment,    -- @Id + @GeneratedValue(IDENTITY)
    name varchar(255) not null,               -- String + @Column(nullable = false)
    price integer not null,                   -- Integer + nullable = false
    stock integer not null,                   -- Integer + nullable = false
    created_at datetime(6),                   -- @Column 없음 → null 허용, 이름은 created_at 으로 번역될 것으로 예측
    updated_at datetime(6),
    primary key (number)
)
```

| 확인할 것 | 예상 |
| :--- | :--- |
| column 이름 | `createdAt` → `created_at` (카멜 → 스네이크) |
| `not null` 개수 | 3개 (`name` `price` `stock`) = `nullable = false` 횟수와 같아야 함 (`number`는 PK라 별도) |
| `@Column` 없는 필드 | column이 **생긴다** (null 허용) |
| 기동 시 순서 | ① 연결 → ② 기존 `product` 테이블 삭제(`drop`) → ③ `create table` |

- 기동이 **서버 없음**으로 실패하면 ①에서 멈춘 것입니다. 테이블을 지우고 만드는 일은 연결된 다음에 벌어집니다.
- 어긋나면 어디가 어긋났는지(이름 / 타입 / 제약) 적어 두세요. 예측이 틀려도 근거를 찾으면 성공입니다.

**SQL 출력 설정** — `show-sql=true`와 `format_sql=true` 두 줄이 하이버네이트가 만든 SQL을 콘솔에 찍습니다. 로그 레벨 설정이 아니라 **`application.properties`** 에 있는 값입니다.

| DAO 메서드 | 예상 SQL 종류 (종류·횟수만 예측) |
| :--- | :--- |
| `insertProduct` | `insert` 1회 |
| `selectProduct` | `select` (프록시라 **언제** 나가는지는 관측으로 확인) |
| `updateProductName` | `select` 1회 + `update` 1회 (호출이 두 번이므로) |
| `deleteProduct` | `select` 1회 + `delete` 1회 |

> SQL 문자열을 직접 지어 쓰지 마세요. 실제 문장은 하이버네이트가 만듭니다.
> `ddl-auto` 값에 따라 달라지는 것: 같은 앱을 **두 번** 띄우면 `create`는 두 번째 기동에서 테이블을 지우고 다시 만들어 **첫 번째에 넣은 데이터가 사라집니다.**

서버를 띄운 뒤 (Windows는 `curl.exe`, Git Bash 권장).

```bash
# 1. 펜 한 건 저장
curl -i -X POST localhost:8080/product -H "Content-Type: application/json" \
  -d '{"name":"펜","price":1000,"stock":100}'
# 예상: 200, {"number":1,"name":"펜","price":1000,"stock":100}  ← createdAt/updatedAt 은 응답에 없다

# 2. 조회
curl -i "localhost:8080/product?number=1"

# 3. 이름 변경 (PUT)
curl -i -X PUT localhost:8080/product -H "Content-Type: application/json" \
  -d '{"number":1,"name":"볼펜"}'

# 4. 같은 요청 한 번 더 POST → number 가 어떻게 달라졌나?
curl -i -X POST localhost:8080/product -H "Content-Type: application/json" \
  -d '{"name":"펜","price":1000,"stock":100}'

# 5. 삭제 → 다시 조회
curl -i -X DELETE "localhost:8080/product?number=1"
curl -i "localhost:8080/product?number=1"            # 없는 번호를 조회하면? (예측 후 관측)

# 6. 앱을 재시작한 뒤 다시 POST → number 는?
```

**한 건이 이어지는 이름 대조표 (펜)**

| 필드 | ① 요청 JSON | ② `ProductDto` | ③ `Product` | ④ column | ⑤ `ProductResponseDto` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `name` | `name` | `String` | `String` | `name` | `String` |
| `price` | `price` | `int` | `Integer` | `price` | `int` |
| `stock` | `stock` | `int` | `Integer` | `stock` | `int` |
| `number` | (없음) | (없음) | `Long` | `number` | `Long` |
| `createdAt` | (없음) | (없음) | `LocalDateTime` | `created_at` | (없음) |
| `updatedAt` | (없음) | (없음) | `LocalDateTime` | `updated_at` | (없음) |

- INSERT에 값이 실리는 column: `name` `price` `stock` `created_at` `updated_at`. `number`는 **실리지 않습니다**(DB가 만듦, 근거 `@GeneratedValue(strategy = GenerationType.IDENTITY)`).
- `createdAt`·`updatedAt`은 **DB에는 있지만 응답에는 없습니다** (`ProductResponseDto`에 필드가 없고, `saveProduct`가 옮기지 않음).

**기록할 것** (강의 "제출 결과물"에 대응)

| 항목 | 기록 |
| :--- | :--- |
| 응답 본문 · status | 화면에서 읽은 값 (코드상 status는 `ResponseEntity.status(HttpStatus.OK)`) |
| 콘솔 SQL의 첫 낱말 | `insert` 등 — 관측한 값만 |
| 첫 `number` / 두 번째 `number` | 두 번째가 1이 아니어도 정상 (DB 상태에 달림) |
| 재시작 뒤 `number` | `ddl-auto=create` 때문에 다시 처음부터인지 확인 |

> 응답 숫자는 외워서 쓰지 말고 **화면에서 읽은 값**을 적으세요. 재시작 뒤에도 이전 데이터가 남아 있다면 `grep -n "ddl-auto" src/main/resources/application.properties`로 값이 `create`인지 확인하세요.

## Step 7: 엔티티 손으로 써 보기

`src/` 밖에 연습 폴더를 만듭니다.

```bash
mkdir -p practice_notes
```

> ⚠️ **연습 파일을 `src/main/java` 안에 만들지 마세요.** `@Entity`가 붙은 클래스를 두면 앱을 띄울 때 **테이블이 하나 더 만들어집니다.** 다 끝나면 `practice_notes` 폴더째 지웁니다.

`practice_notes/PracticeProduct.java` 를 `Product.java`를 **닫고** 아래 조건으로 먼저 직접 써 보세요.

| 요구 | 값 |
| :--- | :--- |
| 테이블 이름 | `practice_product` |
| 기본키 | `Long id` — DB가 자동으로 만들게 |
| 필수 필드 | `String title`, `Integer amount` — 둘 다 null 금지 |
| 선택 필드 | `LocalDateTime registeredAt` |
| Lombok | 쓰지 않음 (생성자·getter·setter 직접) |

다 쓴 뒤 아래와 대조하세요 (빠뜨린 것이 아직 모르는 것입니다).

```java
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.time.LocalDateTime;

@Entity
@Table(name = "practice_product")
public class PracticeProduct {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    @Column(nullable = false)
    private Integer amount;

    private LocalDateTime registeredAt;

    public PracticeProduct() {
    }

    public PracticeProduct(String title, Integer amount, LocalDateTime registeredAt) {
        this.title = title;
        this.amount = amount;
        this.registeredAt = registeredAt;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public Integer getAmount() { return amount; }
    public void setAmount(Integer amount) { this.amount = amount; }
    public LocalDateTime getRegisteredAt() { return registeredAt; }
    public void setRegisteredAt(LocalDateTime registeredAt) { this.registeredAt = registeredAt; }
}
```

**애너테이션이 하나씩 없다면 무엇이 무너지나** (실제로 지우지 말고 표만)

| 없는 것 | 무너지는 것 |
| :--- | :--- |
| `@Entity` | 테이블이 안 생긴다 (JPA가 이 클래스를 아예 보지 않음) |
| `@Id` | 기본키가 없다 |
| `@GeneratedValue` | ID를 직접 넣어야 한다 |
| `@Column(nullable=false)` | null을 막지 못한다 (**테이블은 만들어짐**) |

- 네 개 중 **없어도 테이블은 만들어지는** 것: 3개 (`@Id`는 기동 오류가 나므로 "만들어진다"에서 제외 — 실행해 확인하지는 않았음).

## 클래스별 전체 정리

위 Step을 다 따라 한 뒤, **어느 클래스가 무슨 일을 하고 누가 누구를 부르는지** 한 번에 보는 정리입니다.

### 1. 폴더(패키지)별 역할

```text
day05_jpa/
 ├── controller/   요청이 들어오고 응답이 나가는 입구
 ├── service/      DTO ↔ 엔티티 변환, 시각 채우기 (업무 흐름)
 └── data/
     ├── dto/         요청·응답으로 오가는 "택배 상자"
     ├── entity/      DB 테이블 한 행과 1:1 대응
     ├── dao/         "무엇을 저장하려는가" (의도)
     └── repository/  "어떻게 저장하는가" (JPA가 구현을 만들어 줌)
```

| 폴더 | 한 줄 역할 | 이 폴더가 **하지 않는 일** |
| :--- | :--- | :--- |
| `controller` | 주소·메서드 매핑, JSON 받기, 상태코드 정하기 | 변환, 저장 |
| `service` | DTO → 엔티티 변환, `createdAt`/`updatedAt` 채우기, 결과를 응답 DTO로 변환 | 주소 매핑, DB 호출 코드 |
| `data/dto` | 필드만 들고 다니는 상자 (로직 없음) | DB 저장 |
| `data/entity` | DB 테이블 구조 정의 (`@Entity`) | 요청/응답 모양 |
| `data/dao` | 저장 의도를 메서드 이름으로 선언·구현 (`insert/select/update/delete`) | 상태코드, 변환 |
| `data/repository` | 실제 DB 접근(`save`, `findById`, `delete`) — **직접 구현 안 함** | 업무 판단 |

### 2. 클래스별 정리표

| 클래스 | 폴더 | 종류 | 한 줄 역할 | 들고 있는 것 | 호출하는 대상 |
| :--- | :--- | :-: | :--- | :--- | :--- |
| `ProductController` | controller | 클래스 | HTTP 4개 입구 (`GET/POST/PUT/DELETE /product`) | `ProductService` | `ProductService` |
| `ProductService` | service | 인터페이스 | 업무 목록 선언 (`getProduct` `saveProduct` `changeProductName` `deleteProduct`) | — | — |
| `ProductServiceImpl` | service/impl | 클래스 | 변환 + 시각 채우기 + DAO 호출 | `ProductDAO` | `ProductDAO` |
| `ProductDto` | data/dto | 클래스 | **생성 요청**을 받는 상자 | `name` `price` `stock` | — |
| `ChangeProductNameDto` | data/dto | 클래스 | **이름 변경 요청**을 받는 상자 | `number` `name` | — |
| `ProductResponseDto` | data/dto | 클래스 | **응답**으로 내보내는 상자 | `number` `name` `price` `stock` | — |
| `Product` | data/entity | 엔티티 | DB `product` 테이블의 한 행 | `number` `name` `price` `stock` `createdAt` `updatedAt` | — |
| `ProductDAO` | data/dao | 인터페이스 | 저장 의도 4개 선언 | — | — |
| `ProductDAOImpl` | data/dao/impl | 클래스 | 의도를 Repository 호출로 바꿈 | `ProductRepository` | `ProductRepository` |
| `ProductRepository` | data/repository | 인터페이스 | `JpaRepository<Product, Long>` 상속만 (본문 비어 있음) | — | (Hibernate → MariaDB) |

> "들고 있는 것"이 **필드로 가진 다른 클래스**(의존)이고, DTO/엔티티에서는 **데이터 필드**입니다.
> 인터페이스(`ProductService`, `ProductDAO`)는 "무엇을 할지"만 선언하고, `Impl`이 "어떻게"를 씁니다.

### 3. `name`이 클래스마다 나오는 이유

`name`이 여러 번 선언돼 보이지만 **같은 데이터가 지나가는 길목마다 있는 "그 단계의 상자"** 입니다. 한 상자에서 다음 상자로 **Service가 옮겨 담습니다.**

| 단계 | 어디에 있나 | 형태 | 누가 채우나 |
| :-: | :--- | :--- | :--- |
| ① | 요청 JSON | `"name":"펜"` | 클라이언트 |
| ② | `ProductDto.name` | `String` | Spring이 JSON → 객체로 자동 변환 (`@RequestBody`) |
| ③ | `Product.name` | `String` + `@Column(nullable=false)` | **`ProductServiceImpl`** 이 `product.setName(productDto.getName())` |
| ④ | DB column `name` | `varchar(255) not null` | Hibernate가 INSERT |
| ⑤ | `ProductResponseDto.name` | `String` | **`ProductServiceImpl`** 이 `setName(savedProduct.getName())` |
| ⑥ | 응답 JSON | `"name":"펜"` | Spring이 객체 → JSON으로 자동 변환 |

그 밖에 `name`이 보이는 곳:

| 위치 | 의미 |
| :--- | :--- |
| `ChangeProductNameDto.name` | **바꿀 새 이름**을 받는 상자 (`number`와 한 쌍) |
| `ProductService.changeProductName(Long number, String name)` / `ProductDAO.updateProductName(Long number, String name)` | 그 새 이름이 메서드 인자로 전달되는 모습 |

> 같은 `name`이라도 상자(클래스)가 다른 이유: 요청에는 `number`/시각이 없고, 응답에는 시각이 없고, DB에는 전부 있기 때문입니다. **모양이 다르면 클래스를 나눈다**가 규칙입니다.

### 4. 필드별 "어느 클래스에 있나"

| 필드 | `ProductDto` | `ChangeProductNameDto` | `Product` | `ProductResponseDto` | 비고 |
| :--- | :-: | :-: | :-: | :-: | :--- |
| `number` | ✕ | ✓ | ✓ | ✓ | DB가 만듦 (`IDENTITY`) |
| `name` | ✓ | ✓ | ✓ | ✓ | |
| `price` | ✓ (`int`) | ✕ | ✓ (`Integer`) | ✓ (`int`) | |
| `stock` | ✓ (`int`) | ✕ | ✓ (`Integer`) | ✓ (`int`) | |
| `createdAt` | ✕ | ✕ | ✓ | ✕ | Service가 `now()`로 채움 |
| `updatedAt` | ✕ | ✕ | ✓ | ✕ | Service/DAO가 `now()`로 채움 |

### 5. 흐름 한 장 — POST `/product` (저장)

```text
클라이언트  {"name":"펜","price":1000,"stock":100}
   │
   ▼
ProductController.createProduct(ProductDto)             ← JSON → ProductDto (자동)
   │  productService.saveProduct(dto)
   ▼
ProductServiceImpl.saveProduct(ProductDto)
   │  new Product()  ← dto 값 옮겨 담기 + createdAt/updatedAt = now()
   │  productDAO.insertProduct(product)
   ▼
ProductDAOImpl.insertProduct(Product)
   │  productRepository.save(product)
   ▼
ProductRepository (JpaRepository)  →  Hibernate  →  INSERT  →  MariaDB
   │                                         number 를 DB가 만들어 돌려줌
   ▼
(돌아오는 길) Product(number 채워짐)
   ▼
ProductServiceImpl  ← Product → ProductResponseDto 로 옮겨 담기 (시각은 빼고)
   ▼
ProductController  ← ResponseEntity(200, ProductResponseDto)  ← 객체 → JSON (자동)
   ▼
클라이언트  {"number":1,"name":"펜","price":1000,"stock":100}
```

### 6. 엔드포인트별 흐름 요약

| 요청 | Controller 메서드 | Service | DAO | Repository 호출 | 응답 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `GET /product?number=1` | `getProduct(Long)` | `getProduct` | `selectProduct` | `getReferenceById` | `ProductResponseDto` |
| `POST /product` | `createProduct(ProductDto)` | `saveProduct` | `insertProduct` | `save` | `ProductResponseDto` |
| `PUT /product` | `changeProductName(ChangeProductNameDto)` | `changeProductName` | `updateProductName` | `findById` → `save` | `ProductResponseDto` |
| `DELETE /product?number=1` | `deleteProduct(Long)` | `deleteProduct` | `deleteProduct` | `findById` → `delete` | 문자열 `"정상적으로 삭제되었습니다."` |

- 이름이 한 칸씩 이어집니다: Controller·Service는 `get/save/change/delete`, DAO는 `select/insert/update/delete`, Repository는 JPA 이름(`save/findById/delete`).
- 변환(DTO ↔ 엔티티)은 **Service에서만** 일어납니다. Controller와 DAO는 변환하지 않습니다.
- `number`·`createdAt`·`updatedAt`: 번호는 **DB**, 시각은 **자바 코드(Service/DAO)** 가 채웁니다.

### 7. 스스로 점검

- [ ] 폴더 6개의 역할을 한 줄씩 말할 수 있다.
- [ ] `ProductDto` / `ChangeProductNameDto` / `ProductResponseDto` / `Product`가 왜 4개로 나뉘는지 필드 표로 설명할 수 있다.
- [ ] `name`이 ① 요청 JSON → ② `ProductDto` → ③ `Product` → ④ column → ⑤ `ProductResponseDto` → ⑥ 응답 JSON으로 이어지는 길을 말할 수 있다.
- [ ] 변환을 하는 클래스(`ProductServiceImpl`)와 변환을 하지 않는 클래스를 구분할 수 있다.
- [ ] `number`는 DB가, `createdAt`/`updatedAt`은 자바 코드가 채운다고 말할 수 있다.
- [ ] `PUT`/`DELETE`가 조회(`findById`)를 먼저 해서 Repository 호출이 두 번인 이유를 말할 수 있다.
