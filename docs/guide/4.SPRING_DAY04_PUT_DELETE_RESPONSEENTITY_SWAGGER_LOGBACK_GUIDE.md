## 0. 먼저 알아둘 것

### PUT / DELETE는 무엇을 받나

| 메서드 | 대상(누구) | 바뀔 값(무엇) | 받는 법 |
| :-: | :--- | :--- | :--- |
| PUT | path (`/members/3`) | **body 전체** | `@PathVariable` + `@RequestBody` |
| DELETE | path 또는 query | 없음 | `@PathVariable` / `@RequestParam` |

- DELETE는 "대상만" 알면 되므로 body를 쓰지 않는 것이 관례입니다 (강의 1교시: `DeleteController`에 `@RequestBody`가 0개).
- **메서드 이름이 아니라 애너테이션이 기준**입니다. 강의의 `PutController.postMember`는 이름이 `post`로 시작해도 `@PutMapping`이면 PUT입니다.
- 저장 계층이 없으면 "정말 바뀌었나/지워졌나"는 코드로 증명할 수 없습니다. → Day03 Step 6의 `MemberController`가 이 한계를 해결한 버전입니다.

### 반환 타입별 응답 (강의 2교시)

| 반환 타입 | 응답 | status |
| :--- | :--- | :-: |
| `String` | 글자 그대로 (`MemberDto[name=…]` 같은 `toString()`) | 200 |
| `MemberDto` | JSON으로 자동 변환 | 200 |
| `ResponseEntity<MemberDto>` | status / header / body를 **직접 지정** | 지정한 값 |

- 강의 예제 `member2`와 `member3`는 **body는 같고 status만 다릅니다** (200 vs `HttpStatus.ACCEPTED` = 202).
- 202는 "받았지만 처리는 아직"이라는 뜻이라, 저장 계층이 없는 예제에서는 `ResponseEntity` 사용법을 보이기 위한 값일 뿐입니다.
- 이 프로젝트에서는 `record`라 `toString()`이 `MemberDto[name=kim, …]` 모양입니다 (강의는 클래스라 모양이 다를 수 있음 → 화면이 맞습니다).

### 같은 URL에 매핑이 겹칠 때

`DELETE /api/v1/delete-api/request1`은 `/{variable}`(아무 글자나)과 `/request1`(이 글자 그대로) **둘 다에 형식상 들어맞습니다.**
Spring은 더 구체적인(리터럴) 패턴을 우선하는 것이 일반적이므로 `?email=` 없이 보내면 `/request1`(`byQuery`)이 걸려 **400**이 나올 것으로 **예측**합니다. 보내기 전에 예측하고 Step 6에서 확인하세요.

### Swagger(OpenAPI) 한 장 요약

| 위치 | 역할 |
| :--- | :--- |
| 의존성 (`build.gradle.kts`) | 문서 기능의 출처 (springdoc) |
| 설정 빈 (`SwaggerConfiguration`) | 문서 제목·설명·버전 |
| 컨트롤러 애너테이션 (`@Tag` `@Operation` `@Parameter`) | 설명 보강 (**없어도 endpoint는 문서에 나옴**) |

- **문서 항목을 만드는 것은 매핑 애너테이션**이지 `@Operation`이 아닙니다. `@Operation`은 설명(summary/description)을 더할 뿐입니다.
- 문서 원본 JSON: `/v3/api-docs`, 화면: `/swagger-ui/index.html` (버전에 따라 다를 수 있으니 **열린 주소가 정답**).

### Logback 한 장 요약

| 질문 | 설정 요소 |
| :--- | :--- |
| 어디에 남나 | `<appender>` `class` (`ConsoleAppender` = 콘솔, `RollingFileAppender` = 파일) |
| 어떤 형식 | `<pattern>` |
| 어느 중요도부터 | `ThresholdFilter` `<level>` + `<root level>` |

레벨 순서: `TRACE > DEBUG > INFO > WARN > ERROR`. 기준이 `INFO`이면 `debug()`는 남지 않습니다.

| pattern 토큰 | 채워지는 값 |
| :--- | :--- |
| `%d{yyyy-MM-dd HH:mm:ss.SSS}` | 시각 |
| `%-5level` | 레벨 (5칸 폭, 왼쪽 정렬) |
| `%thread` | 처리한 스레드 이름 |
| `%logger` | `LoggerFactory.getLogger(X.class)`에 넘긴 클래스의 전체 이름 |
| `%msg` | 로그 메시지 |
| `%n` | 줄바꿈 |

`{}` placeholder vs `+` 연결: 출력은 같지만, `+`는 **로그를 남길지 정하기 전에** 문자열부터 만듭니다. 안 남는 레벨(예: DEBUG)에서 낭비가 생깁니다.

## Step 2: PUT · DELETE · ResponseEntity 복습

새로 만드는 것은 없습니다. Day03 Step 5·6 코드를 **설계 관점으로 다시 읽고** 아래 표를 직접 채워 보세요 (강의 1·2교시).

**2-1. `PutController` 세 입구** (`day03_api/controller/PutController.java`)

| 메서드 | 매핑 값 | 최종 URL | 반환 타입 |
| :--- | :--- | :--- | :--- |
| `asString` | `/member1` | `/api/v1/put-api/member1` | `String` |
| `asJson` | `/member2` | `/api/v1/put-api/member2` | `MemberDto` |
| `asEntity` | `/member3` | `/api/v1/put-api/member3` | `ResponseEntity<MemberDto>` |

- 세 메서드의 **매개변수가 같은가?** → 같습니다 (`@RequestBody MemberDto dto`). 입력은 같고 **출력만** 갈립니다.
- `asEntity`의 `return` 분해:

```java
return ResponseEntity.status(HttpStatus.ACCEPTED).body(dto);
//                     └ status를 정하는 부분      └ body를 정하는 부분
```

**2-2. `DeleteController` 두 방식**

| 매핑 | 대상을 받는 곳 | 매개변수 애너테이션 |
| :--- | :--- | :--- |
| `/{variable}` | URL path 마지막 마디 | `@PathVariable` |
| `/request1` | query string (`?email=`) | `@RequestParam` |

- `@RequestBody`가 하나도 없는지 직접 검색해 확인하세요.

```bash
grep -c "@RequestBody" src/main/java/org/example/practice_spring/day03_api/controller/DeleteController.java
```

**2-3. 저장 계층 유무** — `PutController`/`DeleteController`는 입력을 돌려줄 뿐 아무것도 저장하지 않습니다. 반면 `MemberController`(Step 6 of Day03)는 `MemberRepository`에 저장하고, DELETE 후 GET이 404가 되는 것으로 **삭제를 증명**합니다. 이 차이가 곧 강의 6교시 "삭제를 증명하려면 무엇을 더해야 하나"의 답입니다.

## Step 3: Swagger 적용

`day04_api/config/SwaggerConfiguration.java`

```java
package org.example.practice_spring.day04_api.config;

import io.swagger.v3.oas.models.Components;
import io.swagger.v3.oas.models.OpenAPI;
import io.swagger.v3.oas.models.info.Info;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * Swagger(OpenAPI) 문서의 제목/설명/버전을 정하는 설정.
 * - @Bean 인 openAPI() 만 스프링이 관리한다. apiInfo() 는 그 안에서 부르는 보조 메서드일 뿐이다.
 */
@Configuration
public class SwaggerConfiguration {

    @Bean
    public OpenAPI openAPI() {
        return new OpenAPI().components(new Components()).info(apiInfo());
    }

    private Info apiInfo() {
        return new Info()
                .title("practice_Spring Open API")
                .description("Day04 Swagger 적용 실습")
                .version("1.0.0");
    }
}
```

## Step 4: Logback 적용

`src/main/resources/logback-spring.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <property name="LOG_PATH" value="./logs"/>
    <property name="type" value="app"/>   <!-- 아래 ${type} 의 선언. 강의 원본에는 이 선언이 없다 -->

    <!-- 콘솔: INFO 이상만 -->
    <appender name="console" class="ch.qos.logback.core.ConsoleAppender">
        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>INFO</level>
        </filter>
        <encoder>
            <pattern>[%d{yyyy-MM-dd HH:mm:ss.SSS}] [%-5level] [%thread] %logger %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 파일: ./logs/info.log, 날짜가 바뀌면 info_app.날짜.gz 로 보관, 30일치 유지 -->
    <appender name="INFO_LOG" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>INFO</level>
        </filter>
        <file>${LOG_PATH}/info.log</file>
        <append>true</append>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>${LOG_PATH}/info_${type}.%d{yyyy-MM-dd}.gz</fileNamePattern>
            <maxHistory>30</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>[%d{yyyy-MM-dd HH:mm:ss.SSS}] [%-5level] [%thread] %logger %msg%n</pattern>
        </encoder>
    </appender>

    <!-- TRACE > DEBUG > INFO > WARN > ERROR > OFF -->
    <root level="INFO">
        <appender-ref ref="console"/>
        <appender-ref ref="INFO_LOG"/>
    </root>
</configuration>
```

> 강의 4교시 4-4의 "정의된 적 없는 이름"이 바로 `${type}`입니다. 강의 원본은 선언 없이 쓰므로 파일 롤링이 일어나는 날(하루가 지난 뒤) 의도하지 않은 이름이 될 수 있습니다. 여기서는 `<property name="type" .../>`로 선언해 두었습니다.
> 로그 파일(`logs/`)은 실행한 폴더 기준 상대 경로이며, 이 저장소의 `.gitignore`가 `*.log`를 이미 제외합니다.

**예측 → 확인** (콘솔에서 내 메시지로 찾기)

| 요청 | 로그 |
| :--- | :--- |
| `PUT /api/v1/members/1` | `[2026-… ] [INFO ] [http-nio-8080-exec-1] org.example.practice_spring.day03_api.controller.MemberController 회원 수정 요청 id=1, name=lee` 형태 (시각·스레드 이름은 매번 다름) |
| `DELETE /api/v1/members/1` | 같은 형식으로 `회원 삭제 요청 id=1` |
| `PUT /api/v1/put-api/member3`, `DELETE /api/v1/delete-api/...` | **예제 코드가 남긴 줄 없음** (이 컨트롤러엔 `LOGGER`가 없다) |

- `%-5level`의 `-5` 때문에 `INFO` 뒤에 공백이 한 칸 붙습니다.
- `%logger` 자리에는 `LoggerFactory.getLogger(MemberController.class)`의 **클래스 전체 이름**이 찍힙니다. 클래스를 바꿔 쓰면(복붙 실수) 그 이름이 찍혀 드러납니다.
- `LOGGER.debug("…")`는 콘솔/파일 모두 **안 남습니다** (필터 `INFO` + root `INFO`).

## Step 5: 자동 테스트

`src/test/java/org/example/practice_spring/day04_api/Day04ApiTest.java`

```java
package org.example.practice_spring.day04_api;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc;
import org.springframework.test.web.servlet.MockMvc;

/**
 * Swagger 문서(/v3/api-docs)가 설정값과 컨트롤러 애너테이션을 반영하는지 자동으로 검증한다.
 */
@SpringBootTest
@AutoConfigureMockMvc
class Day04ApiTest {

    @Autowired
    MockMvc mvc;

    @Test
    void 문서_제목_버전과_수정_summary가_반영된다() throws Exception {
        mvc.perform(get("/v3/api-docs"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.info.title").value("practice_Spring Open API"))
                .andExpect(jsonPath("$.info.version").value("1.0.0"))
                .andExpect(jsonPath("$.paths['/api/v1/members/{id}'].put.summary").value("회원 수정"))
                // 애너테이션이 없는 컨트롤러의 endpoint 도 문서에 나온다
                .andExpect(jsonPath("$.paths['/api/v1/get-api/hello']").exists());
    }
}
```

## Step 6: 직접 호출해 확인

서버를 띄운 뒤 (Windows는 `curl.exe`, Git Bash 권장).

```bash
# 준비: 회원 한 명 등록
curl -i -X POST localhost:8080/api/v1/members -H "Content-Type: application/json" \
  -d '{"name":"kim","email":"k@x.com","organization":"kyobo"}'

# PUT 세 방식 비교 (강의 5교시) - 같은 JSON, 다른 반환 타입
BODY='{"name":"kim","email":"k@x.com","organization":"kyobo"}'
curl -i -X PUT localhost:8080/api/v1/put-api/member1 -H "Content-Type: application/json" -d "$BODY"   # 문자열 200
curl -i -X PUT localhost:8080/api/v1/put-api/member2 -H "Content-Type: application/json" -d "$BODY"   # JSON 200
curl -i -X PUT localhost:8080/api/v1/put-api/member3 -H "Content-Type: application/json" -d "$BODY"   # JSON 202

# DELETE 두 방식 + 겹치는 URL (강의 6교시) - 보내기 전에 먼저 예측!
curl -i -X DELETE localhost:8080/api/v1/delete-api/hong
curl -i -X DELETE "localhost:8080/api/v1/delete-api/request1?email=k@x.com"
curl -i -X DELETE localhost:8080/api/v1/delete-api/request1               # email 없음: 어느 메서드가 걸리나?
curl -i -X DELETE "localhost:8080/api/v1/delete-api/request1?mail=a@x.com" # key 이름 틀림

# 삭제 증명: 삭제 전후 두 번 조회 (강의 6-5)
curl -i localhost:8080/api/v1/members/1       # 200
curl -i -X DELETE localhost:8080/api/v1/members/1   # 204 + 콘솔에 LOGGER 로그
curl -i localhost:8080/api/v1/members/1       # 404

# 로그 파일 확인 (실행한 폴더 기준)
ls -l ./logs
tail -n 3 ./logs/info.log
```

**기록할 것** (강의 "제출 결과물"에 대응)

| 항목 | 기록 |
| :--- | :--- |
| `member2` vs `member3` | status 숫자(화면 값), body가 같은지 |
| 겹치는 URL `/request1` (email 없음) | 응답 status·본문 → `/{variable}`이 걸렸으면 본문 `request1`, `byQuery`가 걸렸으면 오류 응답. **관측한 값만** 적기 |
| 로그 파일 | 마지막 줄 (콘솔 줄과 같은 형식인가 — 두 appender의 pattern이 같다) |
| 로그가 없다면 | 찾아본 경로를 적기 (`logs`는 실행한 폴더 기준) |

> 응답 코드 숫자는 외워서 쓰지 말고 **화면에서 읽은 값**을 적으세요. 외운 값과 화면이 다르면 화면이 맞습니다.

## 도전 과제

1. **`/swagger-ui` 끄기** — `application.properties`에 `springdoc.swagger-ui.enabled=false`를 넣고 화면이 사라지는지 확인 (개발용 문서를 운영에서 끄는 방법).
2. **`@Operation` 전면 적용** — `MemberController`의 나머지 메서드(`list`/`get`/`create`)와 `ErrorResponse` 응답에 `summary`/`description`을 달고 `/v3/api-docs`에서 반영되는지 보기.
3. **레벨 분리** — `ERROR`만 담는 `error.log` appender를 추가하고 `ThresholdFilter` 대신 `LevelFilter`(`onMatch`/`onMismatch`)로 정확히 ERROR만 받게 만들기.
4. **placeholder 비교** — `LOGGER.debug("값 {}", 객체)`와 `LOGGER.debug("값 " + 객체)`에서 레벨이 INFO일 때 객체의 `toString()`이 언제 호출되는지 `toString()`에 출력문을 넣어 확인하기.
5. **`PutController` 저장 연동** — `PutController`가 `MemberRepository`를 쓰도록 바꿔 "PUT 후 GET으로 실제 변경 확인"이 되는 모양(= `MemberController`)으로 만들어 보기.
